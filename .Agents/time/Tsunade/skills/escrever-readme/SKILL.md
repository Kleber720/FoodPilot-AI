# Escrever um README

1. **Junte a matéria-prima.** O que o dono entregou na delegação: configuração, comandos, contrato, limites conhecidos, resultados de verificação. O que ninguém entregou não existe — pergunte ao dono antes de escrever.
2. **Escreva para quem chega agora.** O que é o projeto, como rodar do zero, como configurar, qual é o contrato ou as rotas, onde ficam os dados, o que não funciona ou não foi verificado. Liste os documentos de `docs/` com uma linha cada — mapa do projeto, domínio, decisões, matriz de regras, dados e monitoramento — para o leitor não procurar no escuro.
3. **Não invente detalhe técnico.** Campo sem informação vira pergunta ao dono, não frase genérica. README com texto que ninguém consegue seguir é pior que README ausente.
4. **Comando no README é comando executado.** Só entra o que alguém rodou, e do zero. O que não foi executado é marcado como não verificado — e o Kakashi usa esses mesmos comandos no [`avaliar-entrega`](../../../Kakashi/skills/avaliar-entrega/SKILL.md).
5. **Atualize no fechamento em que a mudança entra.** README atrasado é README errado: o próximo leitor confia nele.
6. **README não substitui registro e registro não substitui README.** O registro guarda o que deu errado; o README, o que funciona agora.
7. **Preserve o que estava certo.** Não reescreva seção sem relação com a entrega nem mexa no README de outro projeto.
